# Does line mapping help a visitor recognize the right turn?

Anish and Krishna own recording and reconstruction. Arielle owns the guest-view comparison. The first experiment is whether adding LIMAP places walls and doorway edges more accurately on an ordinary walk through a new building. The original hallway remains a development example. Across 33 turn views, supported floor coverage improved from 73.47% to 74.58%, while near-vertical coverage gained only 13 pixels. Some vertical additions landed on furniture. A subsequent fixed-pose Mac trial recovered real line tracks on new recordings. The measured-doorway and reserved-building tests are still open. [Local trial findings](../knowledge/mac-field-mapping.md). [Capture task](https://github.com/darkprince558/path-app/issues/4) · [Measured baseline](https://github.com/darkprince558/path-app/blob/0257711/knowledge/mac-video-trial.md#plane-fills-at-the-turn)

## What to record next

Start with one 15–25 second original MOV or MP4 from each of three buildings. Use the regular camera at 1× and your normal walking pace. Start a few steps before the decision point, round it, and continue a few steps beyond it. Where space allows, keep the same jamb or wall edge in view from both sides. Then add a second, physically different route per building for six routes. A second pass on the same route counts as a repeat.

| Building | First route | Second route |
| --- | --- | --- |
| A | Well-lit textured L-turn with an open doorway | Plain painted corridor with repeated doors |
| B | Wider lobby or T-junction with furniture | Glass entrance, reflective floor or a bright-to-dim transition |
| C · reserved | An ordinary junction chosen before reviewing footage | A harder route with a sloped surface, oblique wall or moving people |

For each clip, save a route ID, building ID, phone/lens, lighting, approximate turn time, and which openings were actually open. Measure one visible length to set the scale and **a different** doorway width for scoring. A short separate reference clip or photo from the side helps a reviewer judge depth, glass and door boundaries. Keep it out of reconstruction. Put source media and measurements under local `captures-local/`. If only one route is available today, run it and keep its result labeled by building.

## Compare three outputs from the same walk

1. **Freeze the baseline.** Save the code revision, settings, selected frames, camera poses and viewer transform. Export the original OpenMVS textured mesh and the current mesh with depth-verified plane fills. Baseline implementation and commands are in [the Mac capture PR](https://github.com/darkprince558/path-app/pull/19).
2. **Add LIMAP as an optional experiment.** Give it the same undistorted images, intrinsics and COLMAP poses. Start with fixed cameras. Reproject recovered 3D line segments onto the original views and inspect the track for the same jamb across multiple camera positions. Use supported segments to bound or trim an existing candidate wall or floor patch. Each patch still needs depth and photo agreement. When the line is ambiguous or unavailable, preserve the baseline result and count the case. Test joint point/line camera refinement separately if fixed-pose evaluation indicates a tracking problem. [LIMAP paper](https://openaccess.thecvf.com/content/CVPR2023/html/Liu_3D_Line_Mapping_Revisited_CVPR_2023_paper.html) · [LIMAP implementation](https://github.com/cvg/limap)
3. **Freeze settings before opening building C.** Keep all passes from one building in the same split. Pick evaluation views and mark actual open doorways, walls, floor, glass and foreground furniture before seeing the reconstructions. Render all three exports from identical cameras. A separate pass can be localized against the frozen model for evaluation. Log a failed localization as a failure. The original hallway's reserved photos shared the underlying camera solution with training views, so that result measures a different question from generalization to building C.

If tracking breaks before the turn, investigate frame selection and camera estimates first. If the poses register but a blank wall stays empty, inspect how far apart the usable viewpoints were. Try a short lateral pass or a depth-assisted capture of that location. Keep the ordinary walk in the results so we learn when to ask someone to rescan.

## What earns another field trial

| Question | What to record per route |
| --- | --- |
| Did tracking survive the bend? | Registered frames out of attempted frames, longest lost interval in seconds, and whether both sides of the junction belong to one connected model. Keep failed exports in the totals. |
| Did lines improve geometry? | Mark corresponding jambs in reference photos. Measure median edge displacement in pixels at a fixed render size and doorway width error in cm using the independent scale length. Report missing or unmeasurable jambs. |
| Did the mesh invent a barrier or opening? | Count real open doorways newly crossed by triangles and real barriers newly depicted as open. Score wall and floor coverage separately and exclude furniture. Show the worst view and its source image. |
| Can a guest use it? | Hide the method labels and vary display order. On a second phone, record which turn or door an unfamiliar viewer chooses from each map, time to first interactive view, asset size and Mac processing time. Human verification of a walkable route stays separate from reconstruction. |

For this pilot, advance LIMAP if it reduces median jamb displacement beyond annotation repeatability on both reserved routes, retains at least as many measurable jambs and connected routes, and introduces zero newly blocked doors or false openings there. Have two people independently mark a small sample to estimate repeatability. Report counts and the worst route alongside the median. If the comparison is inconclusive, keep the current default and use the failure to design the next capture. Six routes support a pilot decision. A broader claim needs fresh buildings, another operator, a different phone including one without LiDAR, and repeat walks under different lighting. Test stairs, ramps, longer loops and outdoor paths as separate conditions before claiming coverage for them.

## What already exists and what to reuse

| System or paper | How it helps Path |
| --- | --- |
| **COLMAP + OpenMVS** | Our existing building blocks estimate camera poses and sparse points, then reconstruct and texture a dense surface. Keep this working Mac pipeline as the control. [Structure-from-Motion Revisited](https://openaccess.thecvf.com/content_cvpr_2016/papers/Schonberger_Structure-From-Motion_Revisited_CVPR_2016_paper.pdf) · [OpenMVS](https://github.com/cdcseacave/openMVS) |
| **AliceVision / Meshroom** | Its video keyframe selector and photogrammetry pipeline through texturing provide an independent RGB reconstruction baseline. Run its documented dense CUDA workflow on an NVIDIA machine when available. Its CPU draft meshing mode is a different comparison. [Video keyframe selection](https://meshroom.readthedocs.io/en/stable/generated/meshroom.nodes.aliceVision.KeyframeSelection.KeyframeSelection.html) · [Photogrammetry stages](https://github.com/alicevision/meshroom-manual/blob/develop/source/feature-documentation/core/pipelines/photogrammetry.rst) · [Hardware requirements](https://meshroom-manual.readthedocs.io/en/latest/first-steps/install/requirements.html) |
| **RTAB-Map** | Its open-source mapping system supports depth sensors and loop closure. On the LiDAR iPhone, make a separate native recording of a matched route to estimate how much a depth sensor helps. Label the sensor-assisted comparison separately from ordinary video. [RTAB-Map project](https://introlab.github.io/rtabmap/) · [Authors’ iOS demonstration](https://www.youtube.com/watch?v=rVpIcrgD5c0) |
| **Manhattan-world Stereo and PlanarRecon** | Furukawa and colleagues addressed weakly textured indoor architecture in 2009. PlanarRecon recovered 3D planes from posed monocular videos in 2022. These are direct precedents for the geometry problem. Their assumptions make oblique walls, furniture and glass valuable test cases. [Manhattan-world Stereo](https://grail.cs.washington.edu/projects/manhattan/) · [PlanarRecon paper](https://openaccess.thecvf.com/content/CVPR2022/papers/Xie_PlanarRecon_Real-Time_3D_Plane_Detection_and_Reconstruction_From_Posed_Monocular_CVPR_2022_paper.pdf) · [Code](https://github.com/neu-3dvi/PlanarRecon) |
| **Matterport and Clew** | Matterport offers phone capture and shareable 3D tours. Clew uses ARKit for indoor path retracing. Phone-based venue viewing and wayfinding each have product precedents. Path can test its contribution by asking whether a visitor recognizes the intended turn from an organizer-verified map. [Matterport phone tours](https://go.matterport.com/spc_freemium_EN.html) · [Clew source](https://github.com/occamLab/Clew) |

For an independent geometry check, select several **ScanNet++** scenes with released reference scans. Feed only iPhone RGB into the Mac pipeline and reserve the laser geometry and evaluation poses for scoring. Align scale once per scene, mask unobserved or anonymized areas, and report surface accuracy and completeness separately at declared distances. **ARKitScenes** provides a second collection of mobile indoor captures, including high-resolution reference depth for a subset. Start with a few scenes and keep campus junctions in the field trial because the guest task needs real route decisions. [ScanNet++ data and evaluation tools](https://scannetpp.mlsg.cit.tum.de/scannetpp/documentation) · [ARKitScenes paper](https://arxiv.org/abs/2111.08897)
