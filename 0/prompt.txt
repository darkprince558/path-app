4. Required field semantics
version — Manifest schema version, initially "1.0".
captureId — UUID issued by Sam's backend when a capture is created; identical across its upload bundle.
createdAt — ISO-8601 UTC timestamp.
device — iPhone model, platform and ARKit scanner identification.
coordinateSystem — Geometry, entrance pose and camera poses must agree: metres, right-handed, Y-up; flattened 4×4 transforms in column-major order.
entrancePose — Camera-to-world/reference transform marking the entrance or capture starting location. Agree explicitly whether this is an actual doorway or simply scan origin.
files — Every uploaded file except manifest.json has its own unique relative path, file type, byte size and SHA-256 checksum. The backend rejects unlisted or missing files.
trackingWarnings — Array of strings for degraded tracking, incomplete surfaces or other capture-quality concerns.

5. Backend validation and storage
1. Create capture via POST /api/captures; backend issues captureId and upload targets.
2. On finalize, verify authenticated owner, manifest schema/version, required paths, safe relative paths (no ../), unique paths, byte sizes, checksums and frame references.
3. Reject broken bundles before processing; never publish raw or failed scans.
4. Run Anish's CPU processor with one active job at a time; use local temporary space for intermediate files.
5. Store source bundles and processed models privately in object storage; store capture, revision, frame, job and approval metadata in Tiger Data PostgreSQL.
6. Publish approved processed revisions only. Keep revision IDs immutable so routes and Gemini landmark cues always reference the correct scan.

PROJECT PLAN - EVENT WAYFINDING
PROBLEM
Visitors reach an event but struggle to find rooms, booths, and activities. Static floor plans are difficult to follow and quickly become outdated.
SOLUTION
A collaborative 3D pathfinding app for indoor/outdoor events. Organizers scan venues using phones, create walkable paths and destinations, then share an event link or QR code. Guests see the shared environment and navigate to a selected location.
MVP DATA FLOW
1. Capture: Use a LiDAR-capable phone to scan a small venue section; export 3D geometry and camera images.
2. Transform: Convert scans into viewable scene assets and a connected waypoint/edge graph. Use manually verified anchors to join sections.
3. Store/share: Upload scene assets to cloud storage; save events, scans, destinations, waypoints, edges, and access permissions in the backend. Organizers approve contributed scans.
4. Navigate: Frontend renders the 3D venue, lets hosts label/connect paths, and runs A*/Dijkstra from a QR-marked start point to a destination.
GEMINI API
Analyze scan images to suggest room numbers, signs, entrances, stairs, and recognizable landmarks; return structured JSON annotations and draft route instructions. Require organizer approval before publishing.
TEAM OWNERSHIP
Sam - backend APIs, database/data model, cloud asset storage, uploads, events and sharing.
Krishna + Anish - phone LiDAR capture, scan-to-3D/graph transformation, alignment and upload integration.
Arielle - frontend, 3D viewer, route creation, interactive pathfinding and event UX.
PRIZE TRACKS
[MLH] Best Use of Gemini API; Organizers Choice: Most Adventurous (help people discover unfamiliar spaces). Phone-only hardware; not entering QNX.
DEMO / DONE WHEN
Scan one real venue section, create an event with two destinations, share via QR, navigate a 3D route, and show an approved contributed scan appear for attendees. Out of scope: automatic scan merging and live indoor positioning.
